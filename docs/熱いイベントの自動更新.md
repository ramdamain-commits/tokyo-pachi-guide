# 熱いイベントの自動更新

公開ページの「近日のイベント」タブ（旧・熱いイベント）のデータを、ユーザーの PC（Windows）のタスクスケジューラで定期的に集めて更新する仕組みの説明。設計の背景は `docs/superpowers/specs/2026-10-30-hot-events-design.md`。

## 現状（2026-11-01 から）: DMM だけで公開する

みんレポが日別レポート・店ページの前に JavaScript のボット確認（`admin-ajax.php` に nonce を POST してクッキーを得てから再読込する方式）を入れたため、自動収集では日別の表が無いページしか取れなくなった。これをプログラムで再現するのはボット確認の回避にあたるので行わない（ユーザー決定）。そのためみんレポの自動収集を外し、DMM の予定一覧（周年バッジ・同日の重なり）だけで公開する。

- `scripts/collect-events.mjs` は既定でみんレポに一切アクセスしない（カテゴリ・店名からの直接引き・店ページのどれも）。`collect-meta.json` に `sources: ["dmm"]` を書く。店の対応表の `minrepoTag`・`minrepoCheckedAt` と `store-stats.json` は前回のまま持ち越し（無ければ空）。`rates.minrepoMatched` は `null`（対応率の急落判定もしない）
- 熱さの点数は停止中。みんレポ由来の要素が取れないので、全件が「強さ不明」になる
- 画面の「近日のイベント」タブは、今日から7日の予定を日付の早い順（同日は同じ店の同日の予定数が多い店→店名順）に並べ、既定 30 件・「もっと見る」で全件。各予定の「みんレポで見る」リンク（店のタグページ。タグが無い店は店名のサイト内検索）から、店の出玉データを人が手で確かめる
- `--with-minrepo`（`useMinrepo: true`）は、みんレポが自動取得を受け付けるようになった場合の再開用。**今は使わない**。`run-collect.ps1` もこの引数を付けない。再開するときは `collect-meta.json` の `sources` に `minrepo` が入り、画面が従来の点数つき表示（熱い順・強さ不明の枠）に戻る

以下の「何を取るか」「熱さの点数の式」「立ち上がり直後」の節は、再開した場合の仕様として残している。

## 全体像

`scripts/run-collect.ps1` が、次の順で1回分の収集を行う。

1. 作業用チェックアウトが `main` で、未コミットの変更が無いことを確かめる（違えば何もせず終わる）
2. `git pull --ff-only`
3. `node --test test/*.test.mjs` → `node scripts/collect-events.mjs` → `node scripts/validate-data.mjs`
4. `data/` に変更があれば `chore(data): 熱いイベントを自動更新 <日付>` でコミットして `git push`（push すると GitHub Pages が更新される）

`scripts/collect-events.mjs` は失敗したときに `data/` を書き換えず、終了コード 1 で終わる。壊れたデータで公開ページを上書きしない。

## いつ動くか

| タスク名 | 契機 | 役割 |
|---|---|---|
| `tokyo-pachi-guide-collect` | 毎週月曜 6:00 | 週次の再収集。DMM の予定は月の途中にも追加され、一覧には未来の予定しか載らないので、こまめに集めて履歴に残す |
| `tokyo-pachi-guide-collect-monthly` | 毎月1日 9:00 | 月初の収集。`New-ScheduledTaskTrigger` に月次が無いので `schtasks.exe` で登録する |
| `tokyo-pachi-guide-collect-logon` | ログオン時 | 電源が切れていて取りこぼした回の穴埋め。直前の成功（`data/collect-meta.json` の `lastSuccessAt`）から 6 日以内なら何もしない。ログオンのたびには集めない |

3つとも `WakeToRun`（スリープ中なら起こす。ただし月次タスクは設定の反映に失敗することがあり、その場合は登録スクリプトが `ok (monthly settings not applied: WakeToRun off)` と表示する）・`StartWhenAvailable`（時刻を逃したら復帰後に実行）・多重起動しない（`IgnoreNew`）・実行時間の上限 1 時間で登録する。

登録は `scripts/register-collect-task.ps1` を一度実行する。すでに同名のタスクがあれば上書きせず「登録済み」と表示して飛ばす（上書きは管理者権限が要ることがある）。

## 何を取るか

| 取得元 | 取るもの | 間隔 |
|---|---|---|
| DMMぱちタウン（`https://p-town.dmm.com/schedules/tokyo`） | 東京都の予定（店名・住所・実施日・媒体・企画名）。約 30 ページ | 1リクエストごとに 2 秒以上あける |
| DMMぱちタウンの来店レポート一覧（`https://p-town.dmm.com/shop_reports?prefecture=13`） | 取材実績（レポートID・店・実施日・取材名）。下の「DMM 取材実績（参考表示）」を参照。初回は最大 100 ページ、以後は差分（最大 10 ページ） | 同上 |
| みんレポ（`https://min-repo.com/`）※現在は取らない（`--with-minrepo` のときだけ） | 店ごとの日別の平均G・平均差枚（通常日の基準、過去イベントの結果、特定日の実効性の計算に使う）。保存するのは計算結果だけで、日別データは保存しない | 同上。同じ URL は 1 回の実行で 1 度しか取らない |

- 収集用の User-Agent（`collect/http.mjs` の `UA`）で自己申告して取る。ブラウザを装う User-Agent には変えない（遮断の回避になるため）
- 以下の2点は `--with-minrepo` のときの動き。みんレポのカテゴリ一覧に出ない店は、店名から店ページを直接引いて探す。日別表の無い店は「スロットの日別データなし」として扱う

### DMM 取材実績（参考表示）

各予定のカードに「DMM取材実績（直近1年）: N回・直近 YYYY-MM-DD「取材名」」を1行出す（0回なら「なし」）。あわせて「DMMの来店レポート」リンク（`https://p-town.dmm.com/shops/tokyo/<dmmShopId>/reports`。`dmmShopId` が数字のときだけ）を出す。`data/dmm-reports.json` が読めないときは、この行とリンクを出さない。

- **取材実績は DMM 自身の企画だけで、他媒体の取材や出玉の結果は含まない。参考表示であり点数には使わない**（並び順にも使わない）。来店レポートの本文に並び人数・差枚の数値があるのは一部だけなので、数値は使わない
- データは `data/dmm-reports.json`（`{ updated, reports: [{ reportId, venue, addressKey, date, title, media }] }`）。`venue` は venues のキーで、来店レポートの住所と venues の住所を正規化して突き合わせて付ける。住所は建物名を落として比較する（`東京都` の除去、丁目・番・号の `-` 化、漢数字の丁目の算用数字化も行う）。同じ住所に複数の店があるときは店名の一致で選び、決まらなければ `null`。今の予定に出てこない店の分は `venue: null` のまま数えるだけで、venues は増やさない。`addressKey`（正規化した住所。venues にもある事実情報）を各レポートに保存し、`venue` が `null` のものは毎回の実行で今の venues を引き直して付け直す（その店が後から予定に出たときに付く。付け直しでは店名を保存していないので、同じ住所に複数の店があれば `null` のまま）。店名は保存しない
- 取得の範囲: 初回（ファイルが無い）は 1 ページ目から順に取り、そのページの最も古い実施日が基準日の 365 日前より古くなったら止める（上限 100 ページ）。2 回目以降は 1 ページ目から取り、既知の `reportId` だけのページに当たったら止める（上限 10 ページ）。365 日より古いものはファイルから捨てる
- 取得に失敗しても収集全体は失敗にしない（参考表示のため）。その回は `dmm-reports.json` を書き換えず前回のまま、ログに 1 行出す。途中のページで失敗したときは、そこまでの分も反映しない（反映すると次回の差分取得で取り残しができる）。ページ送りで存在が分かっているページ（最終ページ以下）の 404/410 も、一時的な遮断の可能性があるので失敗として扱い、最終ページを過ぎた 404/410 だけを終端とする。`dmm-reports.json` が壊れている（JSON として読めない・`reports` が配列でない）ときや、収集中に想定外の例外が出たときも、全体は失敗にせず前回のまま（壊れたファイルを「無い」扱いにして初回の取得をやり直すことはしない）。この収集は失敗の判定のあと・書き出しの直前に行うので、全体が失敗する回には来店レポートを取らない。ファイルの検証（`reportId` の重複・日付・`venue`）でエラーになった回も、書かずに警告だけ出す
- 前提: 一覧の構造は予定一覧と同じ `<li class="unit …>` で、リンクが `/shop_reports/<レポートID>`（店舗IDは無い）。構造が変わって 1 件も読めないときは、ログに出して前回のままにする

### 使わないもの

- **みんレポの自動収集（2026-11-01 から）**: 日別レポート・店ページの前に JS のボット確認が入った。クッキーを得るための POST を再現するとボット確認の回避になるため、取らない。点数の代わりに、画面の「みんレポで見る」リンクから人が手で確かめる
- **ホールナビ**: 収集用の User-Agent に 403 を返す（自動収集を拒否している）。User-Agent を偽装して回避することはしない
- **GitHub Actions**: Actions の実行環境からは DMM が 403 を返した（同じ User-Agent でも家庭回線からは 200）。クラウドの IP が遮断されているとみて、プロキシ等での回避はせず、PC で動かす

## 熱さの点数の式（みんレポを取る場合）

現在は点数を出していない（上の「現状」を参照）。再開した場合の式。

式は `collect/score.mjs` の `SCORE_PARTS` が正本。

| 要素 | 点 | 最大 | 欠測の条件 |
|---|---|---|---|
| `mediaG`（取材・企画の強さ: 平均G） | `clamp(過去の上振れの平均 / 150, 0, 5)` | 5 | 同じ企画・同じ媒体の履歴が 3 回未満 |
| `mediaSamai`（同: 平均差枚） | `clamp(過去の上振れの平均 / 25, -2, 5)` | 5 | 同上 |
| `venueG`（その店の過去のイベント日の上振れ: 平均G） | `clamp(上振れの平均 / 150, 0, 5)` | 5 | その店の履歴が 2 回未満 |
| `venueSamai`（同: 平均差枚） | `clamp(上振れの平均 / 25, -2, 5)` | 5 | 同上 |
| `busy`（店の普段のにぎわい） | `5 × 順位`（東京の店の中での通常日の平均G の順位。0〜1） | 5 | 店の基準が出ていない |
| `overlap`（同じ店・同じ日の重なり） | `min(同日のほかの予定の数, 3)` | 3 | 欠測にならない |

- 点は小数第1位に丸める。`点数 = 10 × 点の合計 / 欠測でない要素の最大の合計`（0〜10）
- 欠けた要素は 0 点にせず、分母からも外す。欠けた要素は画面に「データなし」と出る
- 上振れは必ず「その店の通常日（イベント日でも旧イベント日でもない日）との差」にしてから使う。店どうしで生の平均G・平均差枚は比べない（比べるのは「店の普段のにぎわい」の順位だけ）
- 周年は加点しない（バッジ表示のみ）。「○のつく日」型の企画も加点しない
- `mediaG` と `mediaSamai` の両方が欠測のイベントは「強さ不明」の枠に並べ、強さの出ているイベントと同じ順位に混ぜない

## 立ち上がり直後は全件が「強さ不明」になる

DMM の一覧には未来の予定しか無く、過去の開催をまとめて取れる場所が無い。そのため、集めた予定が過去日になって凍結されたものを履歴として貯める。収集を始めた直後は履歴が無いので、取材・企画の強さと店の過去の上振れは全件が欠測になり、全件が「強さ不明」の枠に並ぶ（強さ不明の予定は点数を出さず、日付順に並べる）。履歴は収集を続けるほど貯まり、1〜2 か月で効き始める見込み。ただし、みんレポから日別表が取れることが前提で、2026-10-31 時点では空ページしか返らず、この状態が続く間は履歴が貯まらない（下の「既知の制約」を参照）。結果（過去日の平均G・平均差枚の差）は、過去日になった後の実行で一度だけ書き込まれ、その後は変わらない。

## 既知の制約

- **みんレポの自動収集は外した（2026-11-01）**: JS のボット確認のため。下の 2026-10-31 時点の観察（空ページ）はこの前段の症状だった。以下はその記録
- **みんレポが収集に空ページを返している（2026-10-31 時点）**: 実データの確認で、みんレポが当方の収集に表の無い空ページしか返さなかった（取得 167 ページ中 166 ページが空。前日は表が取れた店も空だった）。2026-11-01 に 1 ページだけ再確認したところ、日別レポートのページが JS のボット確認（スクリプトで確認用のクッキーを得てから再読込する仕組み）に置き換わっていた。この確認をプログラムで通すのはボット確認の回避にあたるため行わず、みんレポの自動収集は外した（`--with-minrepo` を付けたときだけ動く。今は使わない）。**みんレポを使う形に戻した場合も、この状態が続く間は、みんレポ由来の値（通常日の基準・店の普段のにぎわい・結果・特定日の実効性）が取れず、履歴も貯まらないため、全件が「強さ不明」になる**。回避のための User-Agent の変更や取得間隔の短縮はしない
- 取得した店ページの 8 割超が空だった実行では、収集ログに「構造変更の可能性」の警告が出る（空ページが続く場合も同じ警告になる。サイト側の構造変更と制限・遮断は、警告だけでは区別できない）。このとき、店名からの直接引きで「見つからない」と記録した確認日は取り消し、次回の実行でまた試す
- 取得元の HTML 構造が変わると収集が壊れる。検証で止まり、公開データは更新されない

## PC 側の前提

- 実行時刻に PC の電源が入っているか、スリープ中であること。電源が切れていた回はスキップされ、次のログオン時に穴埋めされる
- ユーザーがログオンしていること（タスクは「ログオン中のみ実行」で登録する）。Windows Update の再起動後に誰もログオンしていなければ走らない
- 作業用チェックアウト（`C:\Users\ramda\projects\tokyo-pachi-guide`）が `main` で、未コミットの変更が無いこと。そうでなければ何もせず終了コード 2 で終わる（人の作業を壊さない）。別ブランチで作業している間は、収集は走らない
- `node.exe` と `git.exe` が使えること（`run-collect.ps1` が PATH と標準のインストール先から探す）
- push の認証が通っていること（資格情報マネージャーに保存済みであること）

## 失敗したときの見方

- **公開ページの最終更新日で判断する**。「近日のイベント」タブの先頭に最終更新日が出る。35 日を超えると古さの警告が出る。`Get-ScheduledTaskInfo` の `LastTaskResult` では判断しない（一度も発火しなかったときも前回の値のまま残る・終了コード 0 には「見送り」も含まれ、データが更新されたとは限らないため）
- 原因は作業用チェックアウトの `logs/collect-<yyyyMMdd-HHmm>.log` を見る（`logs/` は `.gitignore` 済み）。終了コード:
  - `0`: 正常終了（データ更新あり・変更なし・ログオン時に 6 日以内で見送り・別の実行が進行中で見送り、のいずれか）
  - `1`: pull・テスト・収集・検証・commit・push のどれかが失敗。ログにどの段階かが出る。push だけ失敗した場合はコミットが残り、次回の実行で push される
  - `2`: main 以外のブランチにいる、または未コミットの変更がある。何もせず見送った
- 収集（`collect-events.mjs`）や検証（`validate-data.mjs`）が失敗したときは、スクリプトが `data/` を直前のコミットの状態に戻してから（`git restore --worktree --staged data` と `git clean -fd data`）終了する。戻せなかったときはログに警告が出るので、同じ2つのコマンドを手で実行する（戻さないと次回以降が終了コード 2 で見送られ続ける）
- 複数のタスクが同時に発火しても、`logs/collect.lock` を持っている実行が1つだけ進み、ほかは終了コード 0 で見送る（取得元への間隔を守るため）
- 起動直後に `git pull` が失敗したとき（復帰直後でネットワークが未接続など）は、60 秒おいて最大 2 回まで再試行する

## 手で動かす

```powershell
Start-ScheduledTask -TaskName tokyo-pachi-guide-collect
```

実行状況は `logs/` の最新のログで見る。作業用チェックアウトが main で未コミットの変更が無い状態で実行すること。

## 止め方

```powershell
Disable-ScheduledTask -TaskName tokyo-pachi-guide-collect
Disable-ScheduledTask -TaskName tokyo-pachi-guide-collect-monthly
Disable-ScheduledTask -TaskName tokyo-pachi-guide-collect-logon
```

アクセスが拒否されたら、「管理者として実行」した PowerShell で同じコマンドを実行する。再開は `Enable-ScheduledTask`。完全に外すときは `Unregister-ScheduledTask`。
