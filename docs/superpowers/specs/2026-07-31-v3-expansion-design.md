# tokyo-pachi-guide v3 拡張設計（地域拡大＋抽選＋イベント軸）

日付: 2026-07-31
状態: reviewer レビュー済（12件反映）

## 背景・目的

ユーザー依頼3点を1つの拡張として設計する。

1. ○○のつく日など特定日の強化（地域を増やしてよい → 都内主要エリアを広く網羅）
2. 朝の抽選方法の整備（並び順か、店頭抽選か、777コンパス等アプリ抽選か → 全店分を構造化）
3. 取材以外のイベント示唆・イベント（周年・リニューアル等の店固有日／店SNSによる示唆／並び人数・混雑傾向。新台入替は対象外）

## フェーズ構成（案A: 収集一括・機能順次）

どの軸もデータ源が「みんパチ店舗個別ページ＋店公式」で重なるため、店舗ページ訪問を1パスに束ねる。

- **Phase 1**: スキーマ拡張＋検証スクリプト拡張（implementer）→ 新規8エリア収集（researcher 3並列。特定日・抽選・周年・SNS・混雑を1パス収集）
- **Phase 2**: 既存35店の補完スイープ。2段階で行う。
  - ①機械派生: 既存 `lottery.method` に**明記されている**内容だけを読んで `type` / `tool` / `random` を埋める（例:「モバイル抽選(777コンパス)」→ type=app, tool=777コンパス, random=true）。文言から判別できない項目は `null` のまま残し、要確認リストへ出す
  - ②出典再確認: 要確認リストに載った店だけ researcher がみんパチ店舗ページ・店公式を再訪問して埋める（出典URL・checkedAt 更新込み）
  - 「整理券」だけの記述を先着と読む／無記載を `false` と読む、といった**推測での確定はしない**（AI推測補完禁止ルール）。全35店を一律再訪問するより収集コストが下がる
- **Phase 3**: ビューワー拡張＋確認手順doc＋README/CHANGELOG 更新（implementer 1セッション）

工数感: 設計=Fable（本セッション）、収集=Sonnet researcher 3並列×2〜3セッション、ビューワー=Sonnet implementer 1セッション。

## スキーマ拡張（data/stores.json）

### lottery 構造化

現行の自由記述 `method` は残し、機械可読フィールドを追加する。「入場チャネル」と「抽選要素の有無」は別軸なので2フィールドに分離する（例: 店頭整理券には先着番号札＝実質並び順と、シャッフル抽選の両方が実在する）。

```json
"lottery": {
  "type": "lineup" | "onsite" | "app" | null,
  "random": true | false | null,
  "tool": "777コンパス" | null,
  "method": "従来の自由記述（維持）",
  "draw": "9:40",
  "lineup": "9:50",
  "auth": "会員カード要否等（維持）"
}
```

- `type`（入場チャネル）: `lineup`=並びのみ、`onsite`=店頭で整理券/抽選、`app`=アプリ・ツール、`null`=未確認
- `random`（抽選要素）: `true`=入場順がランダム化される、`false`=先着順（並び順・番号札先着）、`null`=未確認
- `tool`: type=app のときのアプリ名。**店舗ページから特定できない場合は null 可**（「モバイル抽選」とだけ書かれた店が既存データに複数ある）。検証は warning 扱い
- **パチ/スロで方式が異なる店**（既存データに「モバイル抽選(スロ)」「整理券(パチ/スロ別抽選)」等が実在）: 共通値をトップレベルに置き、異なる項目のみ `lottery.pachinko` / `lottery.slot` サブオブジェクトで上書きする。差分が出典から判別できない場合は memo に残す
- 777コンパス等ツール利用店は店公式サイト/Xで裏取りする（みんパチ記載が古いことがある）

### 周年・店固有日

既存 `rules` の `annual` 型（match.mjs 実装済・データ未使用）をそのまま使い、任意フィールド `label` を追加する。

```json
{ "type": "annual", "month": 3, "day": 15, "label": "グランドオープン記念" }
```

- match.mjs のマッチングロジックは変更なし。ビューワーで label を表示するのみ

### SNS リンク

```json
"sns": { "x": null, "line": null, "instagram": null }
```

- 値は URL または null。将来チャネル追加はキー追加で対応（3キーを標準とし、欠損キーは null 扱い）
- リンク集の位置づけ。示唆内容そのものは鮮度依存のためデータ化しない（確認手順doc側でカバー）
- 収集元: みんパチ店舗ページのリンク欄 → なければ店公式サイトのフッター/ヘッダー。Web検索での推測取得はしない（別店舗の同名アカウント誤爆防止）

### 混雑参考

```json
"crowd": { "note": "アクセス集中日: 7のつく日", "sourceUrl": "...", "checkedAt": "2026-07-31" }
```

- DMMぱちタウンのアクセス集中日等。参考情報の位置づけで断定表現を避ける

## 収集設計

- 新規エリア（8）: 立川・町田・蒲田・錦糸町・北千住・赤羽・中野・吉祥寺 → 全16エリア。店舗数は郊外激戦区のホール密度が既存都心エリアより高い想定で計60〜90店（収集前のサンプル確認で見積もりを更新する）
- **着手前確認**: 第1ソース（manmai.club/?p=5615）が対象8エリアを収録しているかを先にサンプル確認する。未収録エリアは代替ソース（みんパチのエリア一覧等）を検討してから収集計画を確定する
- ソース序列は既存踏襲: 第1=すろざんまい（curl生HTML＋Python機械抽出、WebFetch要約は照会ごとに数値がぶれるため禁止）、第2=みんパチ（店舗詳細・抽選・周年・SNSの主ソース）。食い違いは各 store の memo に記録
- researcher 3並列の分担（沿線でまとめる）: ①中野・吉祥寺・立川（中央線）②町田・蒲田（南部）③錦糸町・北千住・赤羽（東部・北部）
- researcher 指示に「1店舗1パスで rules / lottery / 周年 / sns / crowd を全部拾う」を明記。出力は `_staging/{エリア}.md` 直書き、完了報告は要約のみ
- 全データに出典URL＋checkedAt 必須（既存ルール）
- DMMぱちタウンのアクセス集中日が JS 描画で curl 不可の場合はメイン側 Playwright 作業に切り出す。収集開始前に1店でサンプル判定する
- Playwright 必須の取得は researcher に割り当てない（既存ルール）

## ビューワー拡張（Phase 3）

- 店カード: 抽選バッジ（type×random から「並び」「店頭抽選」「先着整理券」「アプリ〔ツール名〕」等を表示。**type=null はバッジ非表示**＝「抽選なし」と誤読させない）、周年 rules は該当日に label 付きで表示、SNS・混雑参考リンク
- crowd・SNS 表示には取材タブと同形式の伝聞注記（「媒体・利用者由来の参考情報であり公式発表ではない」）を付ける
- `docs/示唆・イベントの確認手順.md` 新設: SNS示唆・混雑の見方・確認先リンク集（`docs/取材予定の確認手順.md` と同形式）
- 断定的な示唆表現は避け伝聞形式（既存方針踏襲）
- coverage/media 系（取材タブ）は本拡張では変更しない
- README/CHANGELOG を Phase 3 内で更新する
