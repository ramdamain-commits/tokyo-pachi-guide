# 熱いイベント一覧と月次自動更新 設計

日付: 2026-10-30
状態: ユーザー承認済み（2026-10-30）。同日、ホールナビ除外の改訂あり（ユーザー決定）。実装者目線のチェック済み（指摘7件を反映）

## 背景・目的

ユーザーの困りごと（本人の言葉の要旨）:

- 直近のイベントのうち、どれが熱いのかが分からない。毎月の情報は何となく載っているが、度合いが分かりにくい
- 熱いのは周年イベントや特定の来店イベント。逆に「○のつく日」はイマイチなことが多い
- 並びがすごい日は熱いはずなので、並びのような客観的な事実を熱さの根拠にしてよい

現行ビューワ（全83店・16エリア）は「○のつく日」型の旧イベント日パターンが中心で、該当店を同じ重さで並べるだけ。取材は媒体の一般傾向（`media.json`）と過去実績（`coverage.json`）があるだけで、日付つきの予定と熱さの順位は持っていない。

この拡張で、**翌月の東京都の来店・取材・周年イベントを日付つきで自動収集し、客観データに基づく熱さで並べて公開ページに出す**。毎月の更新は人手を介さず自動で回す。

## 決定事項（ユーザー決定）

- 熱さの物差しは「周年・特定の来店イベント＝熱い」「○のつく日＝イマイチ寄り」。並び人数などの客観的事実を根拠にする
- 対象範囲は**東京都全体**。現行83店以外の店でも、熱ければ一覧に出す（エリアで絞り込める）
- 更新は**月初に自動で集計され、公開ページが新しくなる**形。ユーザーが毎月依頼する運用にはしない
- 「○のつく日」の機能は消さない（脇役に下げる）
- **周年は特別扱いしない**。周年であることは表示するが加点はせず、稼働・出玉の実績で他のイベントと同じ物差しで評価する（2026-10-30 ユーザー決定）

## ゴール

1. 公開ページを開くと、今日以降のイベントが熱い順に並んでいる
2. 熱さの点数には根拠の数字が並んで見える（例: 「この企画の過去の開催店は通常日より平均G +600・差枚 +40枚（8回）」「この店の通常日の平均G 2,500（東京で上位20%）」）
3. 月初に人手なしでデータが更新され、最終更新日がページに出る
4. 「○のつく日」が店ごとに実際効いているかを、測れる店では数字で添える

## 非ゴール

- 設定や出玉の予想（「この日は設定6が入る」等の断定）
- X（旧Twitter）の直接収集。API は有料、それ以外はログインが要り、自動化に向かない
- 会員登録やログインが必要な情報の取得（ホールナビの会員限定表示など）
- パチンコの差枚の数値化（みんレポにパチンコ版はあるが、まずスロットのみ。後で追加できる余地は残す）
- 東京都以外への拡大

## アンチゴール（動いても失敗とみなすもの）

- **推測の熱さを事実のように見せる**こと。データが欠けている要素を0点や平均で黙って埋めない。欠測は「データなし」と表示し、点数は分かっている要素だけで出したうえで、欠けている要素を明示する
- 取得元サーバーへの過度な負荷。DMM ぱちタウン利用規約 第6条第1項(7)(8) は過度な負担・妨害を禁止している
- 取得元の文章・画像の丸ごと転載。DMM 規約 第12条で掲載コンテンツの権利は DMM 側に帰属する。表示は事実情報（日付・店名・媒体名・企画名・数値）と元ページへのリンクにとどめる
- 自動更新の失敗に気づけない状態。失敗時に壊れたデータで公開ページを上書きしたり、古いデータを新しいかのように見せたりしない

## 全体の流れ

1. **月次収集（毎月1日・日本時間の朝）**: DMM から当月（1日に回るので「翌月分」は実質当月）の東京都の予定を全件取得する
2. **強さ・実績の付与**: 予定の店をみんレポの店と突き合わせ、過去に集めたイベント（凍結済みの月ファイル）とみんレポの日別実績から、取材の強さと店の実績を計算する
3. **熱さの点数化**: 下記の要素から点数と根拠の一覧を作る
4. **検証**: 検証スクリプトに通す。通らなければ公開データを更新しない
5. **公開**: データファイルをコミットし、GitHub Pages が更新される

**週次の再収集（設計判断・必須）**: DMM の予定は月中にも追加されていく。DMM の一覧には未来の予定しか載らないので、追加分を取りこぼさずに履歴へ残すには、こまめに集めておく必要がある。このため月初の全件収集に加えて、毎週1回同じ処理を回す。

**点数の上書き方針（設計判断）**: 実行のたびに、今日以降のイベントは点数と根拠を上書きする。過去日のイベントは凍結し、後から変えない。

## 熱さの点数

点数は次の要素の組み合わせで作る。重みと式の細部は実装側に任せるが、以下の制約は守る。

2026-10-30 改訂（ホールナビ除外・ユーザー決定）で、材料を DMM とみんレポだけで作る形に組み直した。並び人数の代わりに、みんレポの**平均G（1台あたりの回転数＝稼働）**を客の入りの目安に使う。

| 要素 | 中身 | 出典 |
|------|------|------|
| 取材・企画の強さ | その企画（同じ企画名が少なければ同じ媒体）の過去の開催日に、開催店の平均G・平均差枚が**その店の通常日より**どれだけ上がったか（店をまたいだ平均） | 凍結済みの過去イベント × みんレポ |
| 店の過去の上振れ | その店の過去のイベント日に、平均G・平均差枚が通常日よりどれだけ上がったか | 同上 |
| 店の普段のにぎわい | その店の通常日の平均G。東京の店の中での順位で点にする | みんレポ |
| 重なり | 同じ店・同じ日にほかの予定が重なる | 予定データから集計 |

周年は加点要素にしない（ユーザー決定）。周年であることはバッジで表示する。DMM の予定に「○のつく日」型の企画が入っていた場合も加点しない。その店の「○のつく日」の実効性が測れていれば、その値を根拠欄に添える。

**履歴は自前で貯める（設計判断）**: DMM の一覧には未来の予定しか無く、過去の開催日をまとめて取れる場所が無い。このため、集めた予定が過去日になって凍結されたものを履歴として使う。**収集を始めた直後は履歴が無く、取材の強さと店の過去の上振れはほぼ全件が欠測になる**。収集を続けるほど埋まり、1〜2か月で効き始める見込み（ユーザー了承済み）。

**取材の強さが出ないイベントの扱い（設計判断）**: 取材の強さ（平均G・平均差枚のどちらか）が出ないイベントは、一覧の下部に「強さ不明」の枠を設けてそこに並べる。同じ一本の順位に混ぜて、尺度の違う点数で比べることはしない。

**「イベント日」の定義（設計判断）**: 店の過去の上振れでいうイベント日は、凍結済みの履歴にある取材・来店・周年の日を指す。旧イベント日（○のつく日）は含めない。旧イベント日の効き目は下記「○のつく日の実効性」で別に測る。

制約:

- **比較は店自身の基準に対して行う**。台数や機種構成で店ごとの平均差枚の水準は違うので、店をまたいで生の平均差枚を比べない。「その店のイベント日 − その店の通常日」のように、店の基準を差し引いてから比べる
- 平均G・平均差枚の上振れは、必ずその店の通常日の値を差し引いてから使う。店の普段のにぎわいだけは店どうしの比較になるので、生の平均G を根拠として表示する
- **欠測は欠測のまま扱う**（アンチゴール参照）
- 回数が少ない値（例: 過去の開催が1〜2回）は点数に使わないか、根拠欄に回数を出す
- 点数の横に、効いた要素と数字を必ず並べる（ゴール2）

## 「○のつく日」の実効性

みんレポで旧イベント日に絞り込めるため、店ごとに「旧イベント日の平均差枚 − 通常日の平均差枚」を測れる。83店は `stores.json` の特定日ルールを、83店以外はみんレポの店ページに載っている旧イベント日を使う。測れた店では、既存の今日・明日・日付指定タブと店舗カードの特定日バッジに、この差を添える（例: 「5のつく日: 通常日比 +12枚（直近N回）」）。測れない店は従来どおりの表示とする。

## データの持ち方

- 予定とその熱さ: 月ごとのファイル（例: `data/events/2026-11.json`）。1件ごとに日付・店・媒体・企画名・点数・根拠・出典URL・取得日時を持つ
- 取材の強さ: 企画名・媒体ごとの集計ファイル（例: `data/media-strength.json`）。集計に使った回数を持つ
- 店の実績: 店ごとの統計（通常日の平均G・平均差枚、過去イベント日の上振れ、特定日の実効性）。出典URL・取得日を持つ
- **83店以外の店**: 予定で初めて出てきた店は、名前・住所・自治体と、みんレポの対応名だけを持つ軽い店データにする。既存の `stores.json`（83店）の厳密な検証基準（特定日ルール・抽選方式など）は課さない
- エリア: 83店は既存エリアを使う。それ以外は住所の区市町村で分類し、エリアの絞り込みで選べるようにする
- 既存のデータ方針（全データに出典URLと確認日）を踏襲する

## 店の突き合わせ

DMM とみんレポで店名の表記が揺れる（例: 「エクス・アリーナ東京」「エクス・アリーナ 東京」）。みんレポの店ページには住所が無いため、みんレポとは正規化した店名の一致で対応付ける（あいまい一致はしない）。既存の83店とは住所で対応付ける。みんレポの店名一覧は東京都カテゴリの日別レポート一覧から集める。対応率が低ければ（目安5割未満）、83店以外は実績が欠測だらけになるため、実データでの確認の時点でユーザーに報告する。対応付けられなかった店は、黙って捨てずに件数と一覧を収集ログに出す。

## 自動実行

- 実行基盤は**ユーザーのPC（Windows）のタスクスケジューラ**（2026-10-30 改訂・ユーザー決定）。当初は GitHub Actions を予定していたが、Actions の実行環境からは DMM が 403 を返した（同じ User-Agent でも家庭回線からは 200、みんレポは Actions からも 200）。クラウドの IP が遮断されているため、プロキシ等で回避することはせず、PC で動かす
- 毎週月曜 6:00 と毎月1日 9:00 に動かす。スリープ中なら起こして動かす（WakeToRun）。電源が切れていた回は、次のログオン時に動かす
- 結果のデータをコミットして main へ直接 push し、GitHub Pages を更新する（設計判断）。PR を挟むと「勝手に公開ページが新しくなる」が満たせないため。push するのはデータファイルだけに限る。親 workspace repo のサブモジュール参照は自動では更新しない（従来どおりセッション終了時の手作業で追随する）
- PC 上の作業用チェックアウトを使うため、main 以外のブランチにいる・未コミットの変更がある、といった人の作業中の状態なら、何もせずに終える（人の作業を壊さない）
- アクセスは1リクエストごとに数秒あけ、同じページは1回の実行で1度しか取らない
- 失敗時（取得失敗・検証失敗・突き合わせ率の急落など）は、公開データを更新せず、ログファイルに残して終える。メール通知は無いので、公開ページの「最終更新日」と古さの警告（35日超）で気づける状態にする

## ビューワ

- 新しいタブ「熱いイベント」を追加し、**最初に開くタブ**にする。今日以降のイベントを熱い順に並べる
- 表示は、日付・店名・エリア・取材/企画名・点数・根拠の数字・元ページへのリンク・店の公式Xへのリンク（あれば）
- エリアで絞り込める。日付範囲（今日・今週・今月など）で絞り込めるようにするかは実装側の判断
- **既定の表示は今日から7日間の上位30件（設計判断）**。「もっと見る」で当月の全件を出す。約580件を最初から全部並べると、熱い順にした意味が薄れるため
- 周年のイベントにはバッジを付ける（加点はしない）
- 既存の今日・明日・日付指定・エリア別一覧・取材傾向タブは残す
- 「推定・伝聞であり公式情報ではない」という既存の注記方針を、熱さの点数にも適用する

## 検証・テスト

- 既存の `validate.mjs` / `scripts/validate-data.mjs` を新しいデータファイルにも広げる
- 収集・突き合わせ・点数化は、**マージ前に実データ全件へのドライランを行い、結果を目視確認する**（手打ちのテストでは推測混入を見逃した前例がある）
- 検証の仕組みは、わざと壊したデータ（欠測を0で埋めたもの、日付の範囲外、出典URLなし等）を流して、ちゃんと失敗することを先に確かめる
- 熱さの点数のテストは「店自身の基準との差で比べているか」が崩れたら落ちる入力で書く

## 実装側に任せること

- 点数の重み・式・正規化の細部（上記の制約内で）
- 企画名の表記揺れのまとめ方（同じ企画とみなす範囲）
- 店名正規化の具体的な方法
- データファイルの細かいスキーマ・ファイル分割
- 日付範囲の絞り込みUIの有無
- 週次実行の曜日・時刻
